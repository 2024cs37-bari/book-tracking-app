# Security policy

## Scope

Personal Book Reader handles private library metadata, reading progress, annotations, and original book files. Security priorities are authenticated access, private object storage, integrity verification, safe parsing, and minimal exposure of personal content.

## Reporting a vulnerability

Please do not open a public issue for a suspected security vulnerability. Contact the repository owner through a private GitHub security advisory or private maintainer contact configured on the repository. Include:

- A concise description and affected component/version or commit.
- Reproduction steps or a minimal proof of concept that does not access other people's data.
- Impact and any suggested mitigation.
- Your preferred contact details for follow-up.

Do not include credentials, active signed URLs, personal book files, annotation contents, or other private data. If sensitive data was exposed, revoke/rotate it and report the exposure without forwarding the secret.

There is no guaranteed response or reward policy yet. The maintainer will acknowledge reports when possible, validate impact, coordinate a fix, and publish appropriate release guidance without exposing unnecessary details.

## Security requirements

- Every API route requires authenticated, authorized access.
- R2 remains private; object access uses scoped, short-lived authorization.
- Original file hashes are verified on import and download.
- File parsers and archives are treated as untrusted input and resource-limited.
- Secrets, tokens, signed URLs, and user content are excluded from logs and commits.
- No DRM circumvention is implemented or supported.
- Dependencies and deployment service configuration are reviewed before production.
- App CSP precedes scripts; book frames inherit it and EPUB resources receive a stricter no-script,
  no-network policy before URL creation. Generated hostile EPUB browser tests must pass on engine
  updates; upstream sandbox flags alone are not a security boundary.
- Client-side encryption is not part of the initial baseline; private storage must not be described as end-to-end encrypted.

## Privacy

The product does not require analytics or third-party tracking. Any future telemetry, external metadata enrichment, or diagnostics upload must have a separate documented privacy decision and user-visible behavior.

## Enforced boundaries

The application CSP is generated by `tooling/network-policy.ts` before scripts
are injected. It allows network access to the app itself, the configured sync
origin, and the dictionary service. Set `VITE_DICTIONARY_ENABLED=false` to omit
the dictionary origin entirely. Development websocket permission is limited to
the Vite server's explicit origins; production has no wildcard websocket or
HTTPS permissions. Public sync URLs require HTTPS (except loopback in development or explicit test builds) and reject embedded
credentials, query strings, and fragments. EPUB content keeps its separate,
stricter no-script/no-network policy; app connectivity does not grant a book
permission to contact the network.

The Worker verifies Access RS256 signatures, audience, issuer, and expiry.
`DEV_USER` can bypass authentication only on loopback request URLs. Browser
origins must match the Worker itself or the explicit `CLIENT_ORIGIN`; unset
configuration does not reflect arbitrary credentialed origins. API responses
are private and non-cacheable. The intended deployment is personal; restrict
the Access policy to the owner rather than treating a device ID as identity.

Push JSON is limited during streaming reads, before parsing. Envelopes and
serialized UTF-8 payload sizes are checked; incompatible schema versions are
rejected. Mutation IDs are immutable: retries are idempotent and collisions with
different data are rejected. D1 is scoped by verified user for every query.

Original uploads are streamed to private R2 with a required fixed length and
SHA-256 checksum. R2 verifies the digest before publishing bytes, and clients
verify downloads independently. HEAD confirms only verified originals so an
unverified legacy object cannot justify local eviction. Raw storage errors are
not returned to callers or logged by the application.

## Operational limits

This is not end-to-end encryption. Cloudflare, an authorized account session,
and the device/browser profile can access stored content. Local persistence is
not a backup and browser clearing/eviction can remove it. Keep original files
and metadata backups outside the browser. Remote records currently persist in
an append-only log and R2 until the operator removes them; deleting a book in the
UI is not a guarantee of physical remote erasure.

The server has per-request size limits, but no account storage quota, history
compaction, or application rate limiter. Restrict Access, monitor platform usage,
and consider edge rate limits before admitting more users. The local regression
suite covers Worker behavior, real local D1/R2, and generated JWT signatures;
production Access policy, cookie/preflight behavior, host headers, and platform
quotas require deployment-specific validation. See [API.md](docs/API.md) and
[server setup](server/README.md).

EPUB archives are preflighted before inflation: at most 10,000 entries, 64 MiB
per expanded member, and 256 MiB total expanded content. Duplicate/traversing
paths are rejected. Metadata reads only the container (64 KiB), package document
(1 MiB), and selected cover (8 MiB), rather than expanding book chapters just to
import a title. Extracted metadata text is bounded. PDF and original import
limits are enforced before whole-file allocations.

Dictionary calls require the user's opt-in. Their request and body share a total
deadline, the response is limited to 256 KiB, and concurrent callers cancel
independently. Requests omit credentials/referrers and reject redirects. Parsed
results use a bounded, expiring in-memory cache; they are never uploaded as
telemetry. Production dependencies are checked separately from development-only
tool advisories in CI.
